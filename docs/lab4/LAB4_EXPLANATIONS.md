# Day 4 · คำอธิบายที่ prompt ขอ (4.1A, 4.2B, 4.6)

## 4.1A · RFM

### ทำไมค่าที่เท่ากันต้องได้คะแนนเท่ากัน

สูตรคือ `คะแนน = 1 + floor(5 × จำนวนค่าที่น้อยกว่า / n)` ลูกค้าที่มีค่าเท่ากันจะมี "จำนวนค่าที่น้อยกว่า" เท่ากันพอดี จึงได้คะแนนเดียวกันเสมอ

ถ้าใช้วิธีเรียงแล้วตัดตามตำแหน่ง (เช่น 20% แรกได้ 1) ลูกค้าที่ซื้อ 1 บิลเหมือนกันทุกอย่างจะถูกตัดแบ่งไปคนละคะแนน ขึ้นกับว่าใครอยู่ก่อนในไฟล์ ผลคือ

- คนพฤติกรรมเดียวกันตกไปอยู่คนละกลุ่ม
- เปลี่ยนลำดับข้อมูลนิดเดียว ผลก็เปลี่ยน

ใน test `[1,1,1,1,1,1,7,8,9,10]` ทั้ง 6 ค่าที่เป็น 1 จึงได้ 1 เหมือนกันหมด ไม่ใช่ 1,1,2,2,3,3 ข้อนี้สำคัญกับข้อมูลจริง เพราะสมาชิกจำนวนมากมีจำนวนบิลเท่ากัน (เช่น 1–2 บิล)

### ทำไม R ต้องนับจากวันสุดท้ายของข้อมูล ไม่ใช่วันนี้

R ต้องวัดว่า "ลูกค้าหายไปนานแค่ไหน" ไม่ใช่ "ข้อมูลเก่าแค่ไหน"

ถ้านับจากวันนี้ ทุกคนจะได้วันเพิ่มเท่ากับช่วงที่ยังไม่มีข้อมูลเข้ามา ลูกค้าที่เพิ่งมาเมื่อวันสุดท้ายของไฟล์จะดูเหมือนหายไปหลายวัน ทั้งที่จริงเราแค่ยังไม่รู้

- ตัวเลข "ไม่ได้มา (วัน)" ในรายชื่อจะผิด
- ผลจะเปลี่ยนทุกวันที่เปิดดู ทั้งที่ข้อมูลเหมือนเดิม จึงตรวจซ้ำไม่ได้ และตัวเลขตรวจ "Champions 455 คน" ก็ใช้ไม่ได้

(การเลื่อนทุกคนเท่ากันไม่ทำให้ลำดับเปลี่ยน กลุ่มจึงเหมือนเดิม แต่ค่า R ที่แสดงและความทำซ้ำได้เสียไป)

## 4.2B · ABC

### ทำไมเมนูที่ทำให้ยอดสะสมข้าม 80% ยังเป็นกลุ่ม A

`abc.js` ดู "ยอดสะสม**ก่อน**เมนูนั้น" ถ้าก่อนหน้ายังไม่ถึง 80% แปลว่าเรายังต้องการเมนูนี้เพื่อไปให้ถึง 80% เมนูนี้จึงเป็นส่วนหนึ่งของกลุ่มที่ทำยอด 80% แรก

ถ้าตัดออก กลุ่ม A จะรวมกันได้ไม่ถึง 80% ซึ่งผิดนิยาม กลุ่ม B กับเส้น 95% ก็ใช้หลักเดียวกัน

### ถ้าเปลี่ยนเป็นดูยอดสะสม "หลัง" รวมเมนูนั้น test ข้อไหนพัง

ข้อมูลใน test มียอดสะสม `[0.5, 0.8, 0.9, 0.96, 1]` ผลที่ถูกคือ `A, A, B, B, C` แต่ถ้าใช้ยอดหลังรวม จะได้ดังนี้

- P2 สะสมได้ 0.8 พอดี ไม่น้อยกว่า 0.8 จึงกลายเป็น B
- P4 สะสมได้ 0.96 เกิน 0.95 จึงกลายเป็น C

ผลกลายเป็น `A, B, B, C, C` ข้อที่พังคือ **"เมนูที่ทำให้ยอดสะสมข้าม 80% ยังเป็น A · ข้าม 95% ยังเป็น B"** ส่วนอีก 2 ข้อ (รวมยอดและเรียง, สัดส่วนสะสม) ยังผ่าน

นอกจากนี้ test ข้อมูลจริง **"ABC: เมนูกลุ่ม A 25 รายการ"** ใน `realdata.test.js` ก็จะพังด้วย เพราะเมนูอันดับ 25 คือตัวที่ข้ามเส้น (A รวมกันได้ 80.3%) จะหลุดไปเป็น B เหลือ A แค่ 24 รายการ

## 4.6 · `.github/workflows/analytics.yml`

### ทำงานเมื่อไร

- `schedule: cron "15 23 * * *"` คือทุกวัน 23:15 UTC หรือ **06:15 เวลาไทย** (GitHub อาจเริ่มช้ากว่านี้หลายนาที) และรันเฉพาะจาก branch `main`
- `workflow_dispatch` คือปุ่ม **Run workflow** ในแท็บ Actions สำหรับสั่งรันทันที

### การตั้งค่าส่วนบน

- `permissions: contents: read` ให้สิทธิ์แค่อ่านโค้ด เขียนอะไรกลับเข้า repo ไม่ได้
- `concurrency: analytics` ไม่ให้สองรอบรันซ้อนกัน รอบใหม่จะรอรอบเก่าจบก่อน
- `timeout-minutes: 10` ถ้าค้างเกิน 10 นาทีจะหยุดเอง

### ขั้นตอน (job `build`)

1. `checkout` ดึงโค้ดจาก repo
2. `setup-node` ติดตั้ง Node 22 และเก็บ cache ของ npm
3. `npm ci` ติดตั้ง package ตาม `package-lock.json`
4. **Test analytics functions**: `npx vitest run src/lib/analytics`
5. **Build and write analytics to Firestore**: `node scripts/build-analytics.mjs` คำนวณแล้วเขียน 5 เอกสารลง `analytics/`

### ใช้ secret อะไร

`FIREBASE_SERVICE_ACCOUNT_JSON` คือเนื้อหาไฟล์ service account ทั้งไฟล์ ส่งเป็นตัวแปรสภาพแวดล้อมให้**เฉพาะขั้นที่ 5** สคริปต์อ่านค่านี้แทนการอ่านไฟล์ใน `secrets/` แล้วบันทึก `builtBy: "github-actions"` ลงเอกสาร meta หน้าเว็บจึงขึ้นว่า "โดย GitHub Actions" ค่า secret จะถูกซ่อนเป็น `***` ใน log

### ถ้า test ไม่ผ่าน

- ขั้นที่ 4 ล้ม job จะหยุดทันที ขั้นที่ 5 ไม่ถูกรัน
- **ไม่มีข้อมูลผิดถูกเขียนลง Firestore** หน้าเว็บยังแสดงผลของรอบล่าสุดที่ผ่าน
- รอบนั้นขึ้นสีแดงในแท็บ Actions และ GitHub ส่งอีเมลแจ้งเจ้าของ repo

### ตั้งค่า secret บนเว็บ (ไม่ต้องส่ง key ให้ใคร)

1. เปิด repo บน GitHub แล้วไปที่ **Settings → Secrets and variables → Actions → New repository secret**
2. Name: `FIREBASE_SERVICE_ACCOUNT_JSON`
3. เปิดไฟล์ `secrets/…json` ในเครื่องตัวเอง คัดลอก**ทั้งไฟล์** แล้ววางในช่อง Secret กด **Add secret**
4. ถ้า Action ล้มด้วย `Unexpected token` แปลว่าวางไม่ครบไฟล์ ให้ลบ secret แล้วสร้างใหม่
